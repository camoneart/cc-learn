01何の話か

外部から取り込んだ情報 (Web 検索結果や API 仕様など) を長期記憶に保存すると、時間が経つと古くなる。「API の上限は 100/分」という 2026 年の事実が、2027 年には変わっているかもしれない。期限の仕組みが無いと、古くなった事実が黙って全セッションを誤らせる ── これが note のリスク②「情報汚染の伝播」の、保存した後の側 (封じ込め) の問題じゃ。

この問題への対処を、note とあなたのハーネスは違う手段で解いている。

02note のやり方 — 文書ごとに有効期限を貼る

note S-1.1 の昇格ルール③は、知識を保存するときに「いつ再確認するか」の期限を文書自身に書け、という手段じゃ。

---
type: knowledge
fact: "Vercel 無料枠: 帯域 100GB/月"
source: "WebSearch 2026-03-29 取得"
valid_until: 2026-09-29        # 時刻ベースの有効期限
# または review_by: "次回リリース"  # イベントベース
---

そして定期ジョブや起動時チェックが全知識を走査し、期限を過ぎたものを「⚠ 期限切れ、再確認せよ」とフラグする。note の例「次回リリースで再確認」は、時刻でなくイベント (リリースという事象) を引き金にする形じゃ。

03あなたのハーネスのやり方 — 期限は貼らず、定期に掃除する

あなたのハーネスは、この「文書ごとの有効期限フィールド」を採用していない。代わりに 3 つの別解で同じ目的を達成している:

  • (a) 定期クリーンアップ / 古さ検知 — 文書に期限を貼る代わりに、ドキュメント全体を定期的に見直し、古い前提を整理する運用。C-4 (updated 日付と git commit 日の照合で「自己申告が古い」を検知) が機械側の部分代替。
  • (b) ADR の「撤退条件」 — 重要な意思決定 (ADR) には「どの観測値・事象が出たらこの決定を見直すか」を書く。これは時刻でなくイベント駆動の再確認 = note の「次回リリースで再確認」に近い思想を、最重要の決定に限って持っている。
  • (c) 原則3 (正本共有) — 知識ドキュメントの有効期限という候補は、essence 蒸留で「原則3で吸収」として整理された。真実の源を一箇所に集約し、そこを更新すれば下流が追随する設計で、期限管理の必要を下げる。

04なぜ分岐したのか — あなた自身が棄却した

これは見落としではない。essence の「棄却した候補」表に、はっきり残っている:

| 知識ドキュメントの有効期限 | 260404 B-2 | essence README アンチパターン + 原則3で吸収 |

棄却の理由は、essence README のアンチパターン節「古い前提を残置 → モデル進化との乖離で判断を歪める」+「定期的にドキュメント全体をクリーンアップ…推奨」に対応する。つまり判断はこうじゃ ── 文書ごとに期限フィールドを乱立させるより、全体を定期的に掃除する方が保守的で崩れにくい。フィールドが増えれば管理漏れも増え、期限切れの検知そのものが形骸化しうる。だから「期限を貼る」でなく「定期に掃除する」を選んだ。

06総評

結論はあなたの理解どおり ── 有効期限に関して、あなたのハーネスは note とは異なる実装をしている。ただし「たまたま違う」のではなく、note が示した「文書ごとの有効期限」という手段を評価した上で、フィールド乱立より定期クリーンアップの方が保守的だと判断して退けた、documented な設計分岐じゃ。目的 (陳腐化知識を未来に持ち越さない) は完全に共有しており、達成の道具が違うだけ。note に無い「ADR の撤退条件」というイベント駆動の再確認まで持っている点では、むしろ一部で note を超えている。
