### 3. close 判定を「PR が触れた issue は閉じる」で機械的にやらない

自動 close の挙動を実測した:

| PR body の書き方 | 自動 close |
|---|---|
| `closes #429` (小文字) | **発火する** |
| `Closes #435` | **発火する** |
| `## #428 — ...` (見出しで番号) | **発火しない** |

発火しなかった #428 / #432 は、**残スコープを実測してから個別に判定**した:

- **#432 → close**。処方案 (a)(b)(c) 全部の充足を本文照合で確認し、根拠をコメントに残した
- **#428 → open 維持**。着手レーン自身が PR body で「タイトルが指す問題は閉じていない」と明記しており、閉じると状態を偽ることになる。何が landed し何が残ったかをコメントで記録した

### 5. 暦で発火する処方は、発効前の経路を実装で読んでから通す

#453 が `REMEDIATION_REF_REQUIRED_FROM="2026-09-01"` を導入した。**コミット無しで将来ゲート挙動が変わる**形なので、ゲートで発効前経路を実装レベルで確認した:

- `_REMED_ENFORCED=1` になるのは record ファイル名の日付が発効日以降の時だけ
- それ以前は stderr の warn のみ (block 条件に `_REMED_ENFORCED=1` が AND で入る)
- 日付を読めない名前は「発効前と同じ扱い」で、**到達しない分岐と分かった上で防御として残す**理由が実測ごとコメントに書かれている
- **定数はテストでピン留め済み** (後ろ倒しが執行の無期限先送りになる唯一の経路で、record を書く主体と gate を編集できる主体が同一のため)
