## 5. ゲートの型に足した点

### 5-1. severity は `judging-review-severity` の rubric を**先に**引く

#21 の是正。**fork が付けた severity ラベルをそのまま採らない** — 事実を再測しても、**その事実がどの severity に当たるかは別の判断**。
線は **「コード欠陥 = High / 記述欠陥 = Medium」**。受入基準の全数チェックが第一の判定材料。

### 5-2. close 判定は `closingIssuesReferences` を使う

字句の grep でなく **GitHub のパーサそのものの出力**:

```
gh pr view <N> -R mirinodev/claude-harness --json closingIssuesReferences
```

バッククォート・見出し・大小文字・commit message 側を**すべて一度に**解決する。
**陽性対照**: マージ済み PR に撃つと実際に close された issue と一致する (#496 → #471 #473 で確認)。

**3R の独立レビュアーが持ち込んだ型。** Lead は 2R まで字句 grep で測っていた (結論は合っていた)。

### 5-3. agent がマージを打つ場合の痕跡化 5 段

波 skill は **must** で「`gh pr merge` は人手のみ」と定める。逸脱するなら:

1. **逸脱の宣言** 2. **逐語の転記** 3. **射程の明示** (覆う / 覆わない) 4. **条件充足の表** (痕跡 ID つき) 5. **衝突の事前確認**

実物: `issuecomment-5382749681` (#496) / `issuecomment-5382847302` (#497)。

### 5-4. Monitor は「状態」でなく「遷移」で鳴らす

本波で「いま OPEN でない」を毎周期評価する形を書き、**マージ後に 60 秒ごとに永久に鳴った**。
前回値と比較する形へ直し、**監視対象が閉じたら自分で終了**するようにした。
**鳴りすぎる Monitor は読まれなくなるので、鳴らなすぎるのと同じくらい悪い。**

### 5-5. 「訂正が新しい不正確を生む」を型として認識した (**3 例**)

- #497 2R が新 High を生んだ
- #496 2R が新 Medium を 4 件生んだ
- #497 3R が新 Medium を 2 件生み、**「直した」と宣言した 3 件が主要な着地先で直っていなかった**

**訂正の着地先が PR body / ソースに偏り、issue と record に届かない**のが繰り返し出た (3 回)。
→ **Lead が #498 / #495 へ訂正コメントを足して塞いだ** (body は書き換えず。記録層は遡及改訂しない慣行)。
