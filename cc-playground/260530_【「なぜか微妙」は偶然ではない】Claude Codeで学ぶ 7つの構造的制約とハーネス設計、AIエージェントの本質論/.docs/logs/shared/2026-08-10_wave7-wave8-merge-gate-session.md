### ゲートの型が 2 段 → 3 ラウンドへ育った

第7波は「1 段目 fresh reviewer → 2 段目 fresh agent」の 2 段。第8波で **3 巡目 = メイン自身の直接検証**が加わった。判断基準は残件の性質:

| 残件の性質 | 3 巡目の担い手 |
|---|---|
| テキスト 1 行〜数行 (数値訂正・記述の矛盾) | **メインが grep で逐語確認**。agent 再投入はコスト過剰 |
| コードが動いた | **メインがテストを実走**。#368 (assert 29→30) / #370 で実施 |

### 統合ツリー実走を工程に入れた効果 (最大の収穫)

第8波で **全ペア merge-tree は conflict ゼロなのに、5 本マージすると赤くなる**形を 1 件捕捉した (#363×#370)。git の衝突検査では原理的に見えない class で、**実マージして実走するしか検出手段がない**。

次波以降、この 2 つを別工程として扱う:

- **衝突検査** = 全ペア `merge-tree` (ファイル単位の競合を見る)
- **統合検証** = 全部マージして実走 (意味的な相互作用を見る)

加えて第8波では「共有台帳を触るか」も衝突予測の軸に入れた (第7波で `test-run-all-dispatch.sh` の既知例外リストという共有台帳への追記を予測できず 1 面見落としたため)。

### メイン自身の測定ミス 2 件 (どちらも報告前に自己検知)

**`~/.claude` を clone すると、clone の `origin/*` は「`~/.claude` の local branch」を指す** — GitHub の push 済み状態ではない。これを 2 回踏んだ:

1. 統合ツリーで「統合失敗が消えた」のを見て「未 push を測ったのでは」と疑った (実測で否定。真相はレーンが直前に push していた)
2. #368 の最終検証で `origin/main` が旧 main (`feff190`) のままの clone で測った → GitHub remote (`gh`) を足して測り直し、本当の新 main (`9ed76fc`) で緑を確認してからマージ

**効いた対策**: 2 段目の #370 verifier へこの罠を明示的に警告したこと。警告文を書いた行為が自分の意識にも載り、2 回目を報告前に捕まえられた。

### 規律違反の自己申告 2 件

- **報告経路の確認漏れ**: `claude-code-guide` を起動する時に報告先をファイル指定せず、3 回連続で報告本文が届かなかった。停止して自分で公式ドキュメントを引いて解決。これは第7波で #341 として L1 昇格させた当の規律 (報告様式は agent 型で分岐) を自分が適用し忘れた形。皮肉にも #354 (named 起動前に報告経路を確認する) が L1 に載った直後
- **TaskStop の打ち忘れ 1 件**: 第7波 #350 の報告を回収した後、判定投稿とマージへ直行して明示的な停止を打たなかった (プロセスは自然終了しており放置は発生せず)

### spend limit の扱い (第6波の教訓が効いた)

第7波の 2 段目で 1 体が月次 spend limit で死亡。対処は**分割委譲**:

1. メインが static 側 (diff 確認 + テスト実走) を引き取る
2. limit 解除後、**残り (逆変異・block 経路対照・在庫再走査) だけ**を新 agent へ委譲

「最初からやり直す」より安く、検証の質は落ちない。第6波ログの「limit は実在するが揮発性 — どちらの方向にも決めつけない」がそのまま効いた。

## 設計意図

**なぜ 3 ラウンドにしたか**: 2 段目の残件が「テキスト 1 行」だった時、fresh agent を再投入すると clone・fetch・全数実測に数分かかるのに、判別力は `grep` 1 発と変わらない。**判別力あたりのコストで担い手を選ぶ**のが本旨で、ラウンド数を増やすこと自体が目的ではない。

**なぜゲートの誤りを記録するか**: ゲートは「レーンの主張を疑う」装置だが、**ゲートの主張を疑う層は構造上どこにもない** (2 段目は 1 段目のレポートを渡されて読む立場)。唯一機能したのは**レーンの実測反論**だった。この経路を潰さないことが、ゲート自体の品質保証になっている。
