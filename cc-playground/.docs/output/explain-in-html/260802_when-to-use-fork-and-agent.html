context: fork + subagent の使い分け

2026.08.02運用ガイドClaude Code

01はじめに

context: fork と subagent: の組み合わせは強力なコンテキスト分離手法ですが、すべての作業を別室の専門家に丸投げすれば良いわけではありません。

本資料では、具体的なユースケースを通じて「使うべき場面」と「使わないほうがよい場面」を明確に切り分けます。

02使うべき場面（推奨）

親の「現在の文脈」を引き継ぐ必要があり、かつ試行錯誤のログ（ノイズ）がメインを汚染しやすい重厚なタスクに最適です。

推奨複雑な実装・TDDサイクル

例「この要件を満たすテストを書き、それに合格する実装を行って」

親の会話履歴（要件や設計）を引き継ぎつつ、テストの実行エラーや修正といった泥臭い試行錯誤を別室に閉じ込めることができます。専門家（テスターや実装者）に任せることでコードの質も上がります。

推奨全方位の監査・コードレビュー

例「現在のPR差分に対して、セキュリティとパフォーマンスの観点でレビューして」

大量のファイルを読み込む作業はメインコンテキストを瞬時に使い潰します。別室で security-reviewer 等に徹底的に監査させ、最終的な指摘事項（Verdict）だけをメインに返却させるのが理想的です。

03使わないほうがよい場面（非推奨）

コンテキスト分離のオーバーヘッド（起動コスト）に見合わない、あるいは分離することでシステムが破綻するタスクです。

非推奨軽微な修正や単純なリファクタリング

例「この関数の変数名を変更して」「ここのCSSの余白を調整して」

1〜2行の修正のためにわざわざ別室を用意して専門家を呼ぶのは完全なオーバーエンジニアリングです。メインエージェントが直接ファイルを編集した方が圧倒的に速く、コンテキストも汚染されません。

非推奨ユーザーとの対話が必要な要件定義

例「次に実装する機能の仕様を相談して決める」

サブエージェントは AskUserQuestion を使ってユーザーと直接対話することができません。対話や意思決定は、常にメインコンテキスト（指揮者）の責務として行う必要があります。

非推奨ロングテール知識（ニッチな技術仕様）の解決

例「shadcn-ui の特殊なコンポーネント実装ルールを適用する」

特定のライブラリの細かい仕様を解決するために shadcn-ui-expert のような細かすぎるサブエージェントを作るのは保守負債になります。こうした知識は Skill 単体（またはドキュメント）に逃がし、メインや既存の役割エージェントに読み込ませるべきです。

04判定スコアカード

タスクの性質 context: fork + subagent メインで直接実行
試行錯誤・ログが膨大 最適別室に隔離 避けるメインが汚染される
特定の高度な専門性が必要 最適専門家に委譲 注意指揮者の知識では浅い
軽微な1ファイル修正 避けるオーバーヘッド 最適直接直すのが最速

05総評

「文脈を保ったまま隔離し、専門家に任せる」という特性が活きる重厚なタスク（レビュー・監査・複雑な実装）にのみ適用すること。軽微な作業や対話が必要な作業まで無理にフォークすると、開発スピードが落ちるばかりか、オーケストレーション全体が身動きを取れなくなる。
